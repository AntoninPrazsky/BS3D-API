# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**BS3D-API** is the score service behind the online per-level leaderboards of BS3D (https://github.com/AntoninPrazsky/BS3D): every cleared level the game submits, ranked on two boards per level — this calendar month (UTC) and all time. It runs at the owner's home on a **Raspberry Pi 5 (8 GB)**, published self-contained for `linux-arm64`, reached from the internet only through **Cloudflare Tunnel** — no port is opened on the home router.

It is a separate repository from the game because it targets a different runtime (`linux-arm64`, where the game is `net10.0-windows`), builds on a different CI runner, and lives a different life: the service runs continuously across game releases, and neither may ever need the other to be released.

**The contract is the game's**: contract v1 is written in BS3D#542, and the game's client (BS3D#546, `Game/Online/` in that repository) and its settings (BS3D#548) are built and verified against it. Change the contract there first, then here. What both sides key a board by — the level's file, its `LevelIdentity` hash and `ScoreKeeper.RulesVersion` — is defined in the game's library (BS3D#549); the per-level ceiling table the service whitelists submissions against is written by the game's `Tools/ScoreSim --ceilings` and attached to every game release as `BS3D-<version>-ceilings.json`.

The work is tracked in this repository's issues: **#1** the service (minimal API over SQLite, boards as views over an append-only log), **#2** security (Cloudflare Tunnel, what the service must enforce because the client is open source), **#3** the Pi as host (systemd, backups, a release the Pi pulls), **#4** hardening the Pi (the tunnel token kept off sudo's log, `deploy/cloudflared.service`, SSH, sudo, and the Pi's own nftables firewall, `deploy/firewall.sh`), **#5** the admin page (a separate process on the Pi's loopback, read-only: the views, the launcher, the service's unit kept apart from it and its terminal output stripped of control characters built), **#6** a backup that survives the Pi (to be done).

## Architecture (issue #1)

One ASP.NET Core minimal API, one SQLite file, no ORM.

- `Contracts.cs` — contract v1 as the wire carries it, and every refusal's reason code (`Reasons`). The game's copy is BS3D's `Game/Online/ScoreSubmission.cs`.
- `Endpoints.cs` — `POST /v1/scores`, `GET /v1/boards/{file}`, `PUT` and `DELETE /v1/players/{id}`, and since #7 `GET /v1/boards`, with every check issue #2 says the service must make: a known board (`Ceilings`), a score not over its ceiling, 1–4 stars, shots between the level's fewest and its budget, a duration no faster than `MinSecondsPerShot` per shot, a nickname by the rule, a well-formed game version, per-address and per-player rate limits (429 with `Retry-After`), and a token per player — trusted on first use, stored as its SHA-256, compared in constant time. A repeated `submissionId` is answered with its stored first answer and counts once. Every refusal is one log line with its reason and one entry for `Refusals`, and no line or entry holds a client's address: a rate-limited address is named by the same salted hash the audit column keeps. Nothing about an accepted submission is logged. `GET /v1/boards` (#7, additive to contract v1, recorded in BS3D#685 first) answers every board's #1, its count and the asking player's place in one request, for the game's High Scores screen. Without it, that screen would need one per-board GET per level, over a hundred against a Cloudflare rule of fifty in ten seconds. `ScoreStore.Summary` ranks by the same rule as `Ranked`, partitioned by board instead of filtered to one. With `RequireKnownBoard` on, a board no ceiling table names is left out.
- `ScoreStore.cs` — the schema (applied at every start) and every query. **Boards are views over an append-only log**: a board is the best clear per visible player on `(level file, level hash, rules version)`, over one UTC month or all time, ranked by score and then by arrival (`rowid`), so ties go to the earlier submission. Only `players.name`, `players.hidden` and a submission's stored answer are ever updated in the log; `refusal_days` and `refusal_log` (schema 2) stand outside it: their counts are added to and their old rows deleted. Transactions are plain `BEGIN IMMEDIATE`/`COMMIT` SQL, because Microsoft.Data.Sqlite refuses commands without their `Transaction` set while a `SqliteTransaction` object is open.
- `Ceilings.cs` — every `BS3D-<version>-ceilings.json` in `Scores:CeilingsDirectory` (the union: old game versions stay in the wild). `Scores:RequireKnownBoard` is false in Development only, so a local run takes the test levels the game is pointed at with `levelfile=`. ScoreSim writes the rows in play order, and a row may carry its level's chapter, the level set's `block` (an optional field the game adds); `Ceilings.Levels` keeps each level file's place and chapter from the last table that names it, one that names a chapter before one that does not, for the admin page's boards list. Nothing checks or ranks by either.
- `Nicknames.cs` — 3–16 characters after NFC, trimming and closing runs of spaces; letters, digits, single spaces, `_`, `-`; not a denied name. The game is stricter (only letters its fonts draw).
- `Guards.cs` — tokens, the salted address hash (`CF-Connecting-IP` via the forwarded-headers middleware, trusted from loopback only), the rate windows.
- `Refusals.cs` — every refusal gathered in memory, and `RefusalFlusher`, which writes them every `Scores:RefusalFlushSeconds` and at stop, off the request path: all of them counted per UTC day and reason in `refusal_days`, the recent ones in `refusal_log` (as many as `Scores:RefusalQueueCapacity` per flush, the rest one "dropped" row), pruned to `Scores:RefusalLogDays` and `Scores:RefusalLogMaxRows`. What the admin page will show instead of the journal (#5), whose read access is every unit's lines.
- `AdminCli.cs` — `BS3D.Api admin hide-player|show-player|rename|export|backup|count`, run on the box. The service the tunnel reaches has no admin endpoint, and `AdminSeparationTests` keep it so.
- `AdminWeb/` — the admin page (#5), `BS3D.Api admin web [--port N]`: a separate process of the same binary, dispatched in `Program.cs` before the public service is built. `AdminWebApp` uses an empty builder (no configuration, so `ASPNETCORE_URLS` and `Kestrel:Endpoints` cannot add a listener), listens on 127.0.0.1 only and exits unless that is the one address it got, and refuses to start while any `route_localnet` is 1, or, in one line rather than Kestrel's stack trace, while its port is taken. Its first middleware is the guard: a proxy's header (`CF-Ray`, `CDN-Loop`, `CF-Connecting-IP`, `X-Forwarded-For`, `Forwarded`) is a 403 that stops the page; a Host other than its own a 400; a cross-site `Sec-Fetch-Site` a 403; anything but GET and HEAD a 405; and every answer carries a CSP without scripts and the frame, sniffing and caching headers. `AdminSession` is the login: a printed one-time link (5 minutes, once, void after 5 wrong keys) opens the run's one session, a `SameSite=Strict` cookie, both held as SHA-256 digests. `AdminData` reads through a read-only connection and never selects `token_hash` or `ip_hash` into a result: an address hash stands only in SQL's comparisons and counts (how many addresses a player used, who shares one with whom), and a player's own page letters their addresses A, B… inside the method. A rate-limited address, which the refusal log names by that hash, shows on the live view as "an address". A board is ranked by `ScoreStore`'s own queries, the ones `GET /v1/boards` answers with, and its hidden players are listed apart; the players list sorts by a fixed set of orders, never by the query string; a nickname mixing scripts (Latin with Cyrillic, say) is flagged, so a look-alike is never mistaken for the player it imitates. `Html.M($"...")` is the only way to write HTML: every hole is encoded unless it is already `Markup`, and nothing outside the assembly makes `Markup` (so no Razor, and with it no antiforgery or data-protection key ring). Its one style sheet, `AdminPages.Style.cs`, is served as `/style.css`: the CSP allows no inline style and no font, so the faces are the system's, and the layout is a centred column with tables in panels that scroll sideways on a narrow screen, light or dark after the system's setting. A page that is not a tab names the one it belongs to (`Layout`'s `section`). The boards list goes chapter by chapter in play order when a table names chapters, in play order when none does, every version of a level beside the others, and the boards no table names last. What it prints, its own lines and the console logger's (without colours), goes through `TerminalWriter` on `Console.Out`, set before the logger is made: every control character but the line break (`\n`, or the `\r\n` a Windows console ends its lines with) comes out as `?`, a lone `\r` included. The page stops after 30 minutes without the owner's activity (the live view's own reloads do not count), when its link expires unused, and on SIGHUP, SIGTERM or SIGINT. The owner starts it with `bs3d-admin` (`deploy/bs3d-admin.sh`), which runs `deploy/bs3d-admin-run.sh` through `sudo -n` as `bs3d-api`: only `--port N` passes, into an environment of its own (`env -i`), from `/`, with stdin from `/dev/null`. `deploy/install-admin.sh`, which the owner runs as root, installs both and the sudoers rule for the account that ran it, checked with `visudo` and renamed into place; `update.sh` only says when a release carries a different launcher, so what may run as `bs3d-api` stays the owner's call. Both processes run as `bs3d-api` on a kernel without Yama: the page makes itself undumpable, and `bs3d-api.service` has `/dev/pts` out of reach (`InaccessiblePaths=`), since sudo gives the page a pseudo-terminal that belongs to `bs3d-api`. `PrivatePIDs=yes` was dropped in v0.1.15: under it systemd 257 took the service for a process not its own and stopped it with SIGKILL at once in 3 of 6 stops. `update.sh` puts each release's units in place (since v0.1.9) and puts the ones they replaced back on a rollback.
- **Configuration** is the `Scores` section (`ScoresOptions`), overridden by environment variables (`Scores__AddressSalt`, …). Outside Development the service **refuses to start without `Scores:AddressSalt`** — an unsalted hash of an address is a register of addresses. The content root is the binary's own folder, not the working directory (`Program.cs`): the Pi starts the service in `/var/lib/bs3d-api`, and without its `appsettings.json` the defaults log every request, player ids in the paths included.

**Tests** (`tests/BS3D.Api.Tests`, xunit over `WebApplicationFactory`, a fresh database and a `FakeTimeProvider` per test) cover the ranking cases first — a month board that ignores last month's better score, a tie to the earlier submission, a hidden player gone from every count, a retried id counted once — then every refusal and the player endpoints. The ranking tests were seen to fail: flipping the tie order and dropping the month filter each failed exactly the test written for it. `ProcessTests` starts the built service as its own process, in Production, from a foreign working directory — the factory sets the content root itself and cannot show what the service does on its own; it was seen to fail on both of its assertions before the content root was fixed. `AdminSeparationTests` pin the public route table to the contract and refuse a web root's files and the antiforgery an admin form needs; mapping an admin route, serving a static admin file and adding antiforgery each failed them. `AdminWebTests` host the admin page on a test server over a fresh database (`AdminPage`), and `ProcessTests` start it as a real process in an environment that asks for more than loopback, and on a port already taken; listening on every address, reading configuration without the address check, dropping the proxy tripwire, the Host check, the `Sec-Fetch-Site` check, the session, the link's single use, the encoding, the live view's exemption from activity, the read-only connection or the idle stop, or the check for a taken port, the terminal's filter or setting it on `Console.Out`, and selecting `token_hash`, each failed the test written for it. `AdminViewTests` cover the boards and players views; counting a hidden player on a board, listing every player among a board's hidden ones, showing an address hash instead of its letter, a player sharing an address with themselves, the sort key in the SQL, never flagging mixed scripts and no warning without a ceiling table each failed the test written for it. `BoardsSummaryTests` cover `GET /v1/boards`. Ranking every board as one, dropping the month filter, counting hidden players and listing a board no ceiling table names each failed the test written for it. `RefusalLogTests` write refusals through `RefusalFlusher`; writing on the request path, an unbounded queue, no pruning by age, no pruning by size, an address in a 429's detail, no flush at stop and a timer that never flushes each failed exactly the test written for it. `tests/deploy/tunnel-token.test.sh` tests what root runs on the Pi: `deploy/tunnel-token.sh` against a scratch folder, with stand-ins for `systemctl`, `journalctl` and `cloudflared` on `PATH`. It needs root, because the script refuses anyone else, and writes only to a temporary folder. `tests/deploy/install-admin.test.sh` tests the launcher the same way, the runner through a copy that starts a stand-in for the page; it needs no real root (`unshare -r`). The caller's environment reaching the page, any arguments passing, the port unchecked, stdin from the terminal, no `cd /`, the runner running as anyone, root as the page's owner, a group-writable rule, a launcher that may prompt, no `visudo` check and the owner's name unchecked each failed the test written for it. For the boards list, `AdminViewTests` failed on boards sorted by name rather than play order, a chapter ignored, a chapter taken only from the row a board kept (when two tables name a board, the first read is kept, and a release read after a newer development build's table names no chapter), and a table without chapters taking them away. The last is why the name is checked: `nobody ALL=(ALL) NOPASSWD: ALL #` as a name makes a rule that `visudo` takes, and that makes `nobody` root. `tests/deploy/update.test.sh` runs `update.sh` over releases packed as `release.yml` packs them, served by a stand-in for curl, with one for systemctl that records which release and which unit each restart met; units never installed, installed 0600, reloaded after the restart, every unit installed every time, a unit's mode not looked at, the timer never re-armed and a rollback that keeps the failed release's units each failed the test written for it. `tests/deploy/firewall.test.sh` runs `deploy/firewall.sh` with stand-ins for `ip`, `systemctl`, `systemd-run` and `nft`. The exception is `nft -c`, which the real nft makes in a network namespace of its own, so the rules written are the rules checked and nothing is ever loaded into the machine running the test. Each of these failed the test written for it: the undo armed after the rules load, no check before writing, addresses instead of prefixes, a confirm that does not look at what is loaded, no backup of the old file, `--remove` leaving the rules file, and rules nft cannot read. `tests/deploy/firewall-lab.sh` then runs the script itself, with the real `ip` and `nft`, in a network namespace wired by a veth cable to a "router" namespace, while UDP and TCP flows that predate the rules run over IPv4 and IPv6, speaking every 2 s. It checks that:
- every flow still gets the far end's data after the load;
- new outbound connections connect, with the neighbour caches emptied;
- from the home network port 22 is open and 8080 is dropped;
- from addresses outside its prefixes, 22 is dropped too, over IPv4 and IPv6.

Each of these failed it: the rules loaded straight away with no warm-up (the 2026-10-02 outage, every flow cut), the warm-up after the rules, SSH open to any source, and no ICMP (IPv6 gone with neighbour discovery). The lab also runs `--confirm` against the real nft five times. In v0.1.16 the check read nft's listing through `grep -q` under `pipefail`: grep stopped at the match, nft died of SIGPIPE writing the rest, and loaded rules looked absent (on the Pi, and 0 times of 5 in the lab). The check now reads the whole listing first. The nft stand-in writes its listing in pieces, as nft does, so the unit test fails on that too.

## Build, test, run

```powershell
dotnet build BS3D.Api.slnx
dotnet test BS3D.Api.slnx

# Listens where the game's local runs expect it: Settings.json "server": "http://localhost:5000"
dotnet run --project src/BS3D.Api --urls http://localhost:5000

# What the Pi runs
dotnet publish src/BS3D.Api/BS3D.Api.csproj -c Release -r linux-arm64 --self-contained true -o publish
```

The deploy scripts, on Linux only (the Pi, WSL or CI):

```bash
shellcheck deploy/*.sh tests/deploy/*.sh
sudo tests/deploy/tunnel-token.test.sh
sudo tests/deploy/install-admin.test.sh     # or: unshare -r tests/deploy/install-admin.test.sh
sudo tests/deploy/update.test.sh            # or: unshare -r tests/deploy/update.test.sh
sudo tests/deploy/firewall.test.sh          # or: unshare -rn tests/deploy/firewall.test.sh
```

`.github/workflows/build.yml` builds, tests (both suites, and shellcheck over the deploy scripts) and publishes for `linux-arm64` on every push, on `ubuntu-latest` — free, because the repository is public.

## Conventions

The same as BS3D's, deliberately, since one owner and the same agents work on both:

- **Branches are the unit of work, and there are no pull requests.** A branch off `origin/main` named `<issue-number>-<slug>`, merged into `main` with `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`, pushed, and deleted locally and on the remote in the same breath.
- **Line endings are LF**, and `.gitattributes` says so.
- **Nothing secret is ever committed**: the tunnel's token, the salt for hashed addresses and the database live on the Pi only. The code is public on purpose — the security model (#2) assumes an attacker has read it.
- **Tests come with the behaviour**, unlike the game, which has none: a ranking can be wrong on every level while every number in it looks right (BS3D#173 is that failure in the game's own scoring), and the cases that catch it are cheap to write here.
- Comments and documents are load-bearing: change them in the same commit as the behaviour, and state a number only when it was measured.
- The owner communicates in Czech; code, comments and documents are in English.

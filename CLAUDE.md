# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**BS3D-API** is the score service behind the online per-level leaderboards of BS3D (https://github.com/AntoninPrazsky/BS3D): every cleared level the game submits, and since #8 every unfinished attempt (0 stars), ranked on two boards per level — this calendar month (UTC) and all time. It runs at the owner's home on a **Raspberry Pi 5 (8 GB)**, published self-contained for `linux-arm64`, reached from the internet only through **Cloudflare Tunnel** — no port is opened on the home router.

It is a separate repository from the game because it targets a different runtime (`linux-arm64`, where the game is `net10.0-windows`), builds on a different CI runner, and lives a different life: the service runs continuously across game releases, and neither may ever need the other to be released.

**The contract is the game's**: contract v1 is written in BS3D#542, and the game's client (BS3D#546, `Game/Online/` in that repository) and its settings (BS3D#548) are built and verified against it. Change the contract there first, then here. What both sides key a board by — the level's file, its `LevelIdentity` hash and `ScoreKeeper.RulesVersion` — is defined in the game's library (BS3D#549); the per-level ceiling table the service whitelists submissions against is written by the game's `Tools/ScoreSim --ceilings` and attached to every game release as `BS3D-<version>-ceilings.json`.

The work is tracked in this repository's issues: **#1** the service (minimal API over SQLite, boards as views over an append-only log), **#2** security (Cloudflare Tunnel, what the service must enforce because the client is open source), **#3** the Pi as host (systemd, backups, a release the Pi pulls), **#4** hardening the Pi (the tunnel token kept off sudo's log, `deploy/cloudflared.service`, SSH, sudo, and the Pi's own nftables firewall, `deploy/firewall.sh`), **#5** the admin page (a separate process on the Pi's loopback, read-only: the views, the launcher, the service's unit kept apart from it and its terminal output stripped of control characters built), **#6** a backup off the Pi's disk (a microSD card or USB drive, `deploy/backup-card.sh`, built; an encrypted off-site copy to come), **#8** unfinished attempts (BS3D#716), **#9** charts on the admin page (the first ones built), **#10** notes: a player's line about what they saw, from the game's Send a Note (BS3D#813), with its context and, unless the player unticked it, a JPEG.

## Architecture (issue #1)

One ASP.NET Core minimal API, one SQLite file, no ORM.

- `Contracts.cs` — contract v1 as the wire carries it, and every refusal's reason code (`Reasons`). The game's copy is BS3D's `Game/Online/ScoreSubmission.cs`.
- `Endpoints.cs` — `POST /v1/scores`, `GET /v1/boards/{file}`, `PUT` and `DELETE /v1/players/{id}`, and since #7 `GET /v1/boards`, with every check issue #2 says the service must make: a known board (`Ceilings`), a score not over its ceiling, 0–4 stars, shots between the level's fewest and its budget, a duration no faster than `MinSecondsPerShot` per shot (0 stars, an unfinished attempt since #8, skips the two floors, the fewest shots and the duration, and keeps every upper bound), a nickname by the rule, a well-formed game version, per-address and per-player rate limits (429 with `Retry-After`), and a token per player — trusted on first use, stored as its SHA-256, compared in constant time. A repeated `submissionId` is answered with its stored first answer and counts once. `personalBest` means the player's row on the all-time board got better: a first or better clear, or, for a player who has never cleared the board, a better unfinished attempt. Every refusal is one log line with its reason and one entry for `Refusals`, and no line or entry holds a client's address: a rate-limited address is named by the same salted hash the audit column keeps. Nothing about an accepted submission is logged. `GET /v1/boards` (#7, additive to contract v1, recorded in BS3D#685 first) answers every board's #1, its count and the asking player's place in one request, for the game's High Scores screen. Without it, that screen would need one per-board GET per level, over a hundred against a Cloudflare rule of fifty in ten seconds. `ScoreStore.Summary` ranks by the same rule as `Ranked`, partitioned by board instead of filtered to one. With `RequireKnownBoard` on, a board no ceiling table names is left out.
- `ScoreStore.cs` — the schema (applied at every start) and every query. **Boards are views over an append-only log**: a board is the best clear per visible player on `(level file, level hash, rules version)`, over one UTC month or all time, ranked by score and then by arrival (`rowid`), so ties go to the earlier submission. Unfinished attempts (0 stars, #8, the owner's rules in BS3D#716): every clear ranks above every unfinished attempt, and a player's row is their best unfinished attempt in the period only while they have no clear on the board in any month. Once they clear it, their unfinished rows leave every period's board, earlier months' too, so `Ranked` and `Summary` read whether a player has cleared over all of the board's rows (a window) before they pick the period. Only `players.name`, `players.hidden` and a submission's stored answer are ever updated in the log; `refusal_days` and `refusal_log` (schema 2) stand outside it: their counts are added to and their old rows deleted. Transactions are plain `BEGIN IMMEDIATE`/`COMMIT` SQL, because Microsoft.Data.Sqlite refuses commands without their `Transaction` set while a `SqliteTransaction` object is open.
- **Notes (#10)**, `Endpoints.Notes.cs`, `Notes.cs`, `ScoreStore.Notes.cs`: `POST /v1/notes`, additive to contract v1 and recorded in BS3D#813 first. **Anyone may send one, with a picture, onto a disk at the owner's home** (the owner's two answers, 2026-10-06: anyone, and a screenshot the player can untick), so it is held tighter than a score:
  - **its own request size**, `Scores:NoteMaxRequestBytes`, set as endpoint metadata the routing applies before the body is read, while every other request stays at Kestrel's 4 KB;
  - **limits per address**, by the minute and by a sliding 24 hours (`RateLimits.TryTake` with a window), an IPv6 address counted by its /64 (`AddressHasher.NetworkOf`: one host is handed a whole /64), **a global count per UTC day** read in the database inside the write lock, whose 429 waits until midnight, and **a cap on the notes stored** (`Scores:NotesMaxStored`, a 429 `notes-full`), which bounds what notes add to the database the nightly backup copies;
  - **the text** composed to NFC, its line breaks made LF, tabs spaces, trimmed, and no other control character (`NoteText`);
  - **the context** a JSON object within `Scores:NoteMaxContextBytes` whose every name and string decodes as text, stored as it came (a lone surrogate's escape stored raw broke every reader of the note: the review of the first merge);
  - **the picture** base64 that decodes within `Scores:NoteMaxPictureBytes` to something shaped like a JPEG (`Jpeg.TryMeasure` walks SOI, the segments to a frame header with its size, the first scan, and EOI as the last two bytes; nothing is decoded) no wider or taller than `Scores:NoteMaxPictureSide`;
  - **a cap on the pictures kept together**, past which a note is stored without its picture and answers `screenshotStored: false`.

  **A picture is a file, `note-pictures/<id>.jpg` beside the database, not a row** (`ScoreStore.PicturesDirectoryFor`): in the database the nightly backup copied every picture every night into thirty copies on the box and a year's on the card, and a sum of the pictures' sizes read every one of them inside the write lock (SQLite walks a BLOB's pages to reach a column after it). As files they are held to their cap exactly and are not backed up; the words and the context are. A note's `playerId` with the bearer token links it to a player who exists and whose token it is (a wrong token is a 401); a note makes no player, so a newcomer's note keeps its `name` as an unverified claim, with the id and the token's hash it came with. A repeated `noteId` is answered with its stored first answer before any limit but the address's, so a retry of the day's last note still gets its 200. **The `notes` table (schema 3) is outside the score log**: a note can be deleted with its picture, and a player's removal takes their notes and pictures, the linked ones and a newcomer's whose id and token are now theirs. A refused note's log line holds its length, never its text, and every refusal's detail is cut to `Refusals.TextLength` before it is logged (a 600 KB request made one line of a `gameVersion` 500 KB long).
- `Ceilings.cs` — every `BS3D-<version>-ceilings.json` in `Scores:CeilingsDirectory` (the union: old game versions stay in the wild). `Scores:RequireKnownBoard` is false in Development only, so a local run takes the test levels the game is pointed at with `levelfile=`. ScoreSim writes the rows in play order, and a row may carry its level's chapter, the level set's `block` (an optional field the game adds); `Ceilings.Levels` keeps each level file's place and chapter from the last table that names it, one that names a chapter before one that does not, for the admin page's boards list. Nothing checks or ranks by either.
- `Nicknames.cs` — 3–16 characters after NFC, trimming and closing runs of spaces; letters, digits, single spaces, `_`, `-`; not a denied name. The game is stricter (only letters its fonts draw).
- `Guards.cs` — tokens, the salted address hash (`CF-Connecting-IP` via the forwarded-headers middleware, trusted from loopback only), the rate windows.
- `Refusals.cs` — every refusal gathered in memory, and `RefusalFlusher`, which writes them every `Scores:RefusalFlushSeconds` and at stop, off the request path: all of them counted per UTC day and reason in `refusal_days`, the recent ones in `refusal_log` (as many as `Scores:RefusalQueueCapacity` per flush, the rest one "dropped" row), pruned to `Scores:RefusalLogDays` and `Scores:RefusalLogMaxRows`. What the admin page will show instead of the journal (#5), whose read access is every unit's lines.
- `AdminCli.cs` — `BS3D.Api admin hide-player|show-player|rename|export|backup|count`, and since #10 `notes [--after <id>] [--out <folder>]` (one JSON line per note, its pictures written as files: how an agent reads them on the box) and `delete-note <id>`, run on the box. **`count` does not count notes**: `update.sh` compares its line before and after an update as text, and the line before is printed by the release being replaced. The service the tunnel reaches has no admin endpoint, and `AdminSeparationTests` keep it so.
- `AdminWeb/` — the admin page (#5), `BS3D.Api admin web [--port N]`: a separate process of the same binary, dispatched in `Program.cs` before the public service is built. `AdminWebApp` uses an empty builder (no configuration, so `ASPNETCORE_URLS` and `Kestrel:Endpoints` cannot add a listener), listens on 127.0.0.1 only and exits unless that is the one address it got, and refuses to start while any `route_localnet` is 1, or, in one line rather than Kestrel's stack trace, while its port is taken. Its first middleware is the guard: a proxy's header (`CF-Ray`, `CDN-Loop`, `CF-Connecting-IP`, `X-Forwarded-For`, `Forwarded`) is a 403 that stops the page; a Host other than its own a 400; a cross-site `Sec-Fetch-Site` a 403; anything but GET and HEAD a 405; and every answer carries a CSP without scripts and the frame, sniffing and caching headers. `AdminSession` is the login: a printed one-time link (5 minutes, once, void after 5 wrong keys) opens the run's one session, a `SameSite=Strict` cookie, both held as SHA-256 digests. `AdminData` reads through a read-only connection and never selects `token_hash` or `ip_hash` into a result: an address hash stands only in SQL's comparisons and counts (how many addresses a player used, who shares one with whom), and a player's own page letters their addresses A, B… inside the method. A rate-limited address, which the refusal log names by that hash, shows on the live view as "an address". A board is ranked by `ScoreStore`'s own queries, the ones `GET /v1/boards` answers with, the boards list counts its players by `ScoreStore.Summary`, so a count is the length of the board the game shows, and its hidden players are listed apart; a 0-star row reads "unfinished" wherever a row is listed (#8); the players list sorts by a fixed set of orders, never by the query string; a nickname mixing scripts (Latin with Cyrillic, say) is flagged, so a look-alike is never mistaken for the player it imitates. `Html.M($"...")` is the only way to write HTML: every hole is encoded unless it is already `Markup`, and nothing outside the assembly makes `Markup` (so no Razor, and with it no antiforgery or data-protection key ring). Its one style sheet, `AdminPages.Style.cs`, is served as `/style.css`: the CSP allows no inline style and no font, so the faces are the system's, and the layout is a centred column with tables in panels that scroll sideways on a narrow screen, light or dark after the system's setting. A page that is not a tab names the one it belongs to (`Layout`'s `section`). The boards list goes chapter by chapter in play order when a table names chapters, in play order when none does, every version of a level beside the others, and the boards no table names last. What it prints, its own lines and the console logger's (without colours), goes through `TerminalWriter` on `Console.Out`, set before the logger is made: every control character but the line break (`\n`, or the `\r\n` a Windows console ends its lines with) comes out as `?`, a lone `\r` included. The page stops after 30 minutes without the owner's activity (the live view's own reloads do not count), when its link expires unused, and on SIGHUP, SIGTERM or SIGINT. The **Notes** tab (#10) lists the newest notes (the linked player's nickname now, else the claimed name marked unverified, else anonymous) and a note's page shows its text, its context field by field and its picture, served by this process only as `/note.jpg` under the CSP's `img-src 'self'`; the overview counts them. On a database not yet at schema 3 the overview reads no notes and shows its schema warning. The **Charts** tab (#9) draws SVG on the server, with no script and no inline style. `AdminData.ReadCharts` computes one value per UTC day of a fixed range (`?range=14d|90d|all`, never passed to SQL as text; an unknown one is 90 days). No range starts before the first day anything was recorded, so a young service's few days are not squeezed against the right edge by zeros from before it ran. It computes:
  - players and clears in all, counting those before the range;
  - the players who played each day, split into first day (their first submission) and returning;
  - clears and unfinished attempts per day;
  - boards with a clear (a board counts from its first clear; a loss does not count);
  - minutes played per day;
  - refusals per reason, the most frequent first.

  `AdminPages.Charts` draws the bars and lines. Its colours are the style sheet's classes `c1` to `c6`, light and dark. Every bar and point has an SVG `<title>` to read on hover, and every chart has its numbers in a table under it. The axis steps by 1, 2 or 5 times a power of ten, and never by less than 1 for counts. A bar is at most 28 units wide, so a few days' bars stay bars. The last day's label ends at the chart's edge. A chart's x axis (`XAxis`) is days, categories or levels. A chart across the page is drawn 1120 units wide rather than scaled up from 560, so its text stays the size of the others', and on a phone it scrolls sideways in its panel, as tables do.

  Two more charts:
  - **The boards list** opens with the **funnel** (`AdminData.ReadFunnel`): every level a table names, once, all its versions together, in the list's chapter order. Each bar is the visible players who cleared the level and, stacked on top, those who tried it and never cleared any version of it. The bars drop where players stop. Chapters are numbered under the plot, set off by dashed lines, and keyed under the legend.
  - **A board's page** shows its all-time rows in tenths of its ceiling, clears and unfinished attempts apart, when a table names a ceiling. The last tenth runs up to the ceiling itself. The overview reads `backups/last-offbox`, which `deploy/backup.sh` writes on every run about the copy off the box (#6), and warns when none is set up, the last copy failed, or the newest good one is over two days old. The owner starts it with `bs3d-admin` (`deploy/bs3d-admin.sh`), which runs `deploy/bs3d-admin-run.sh` through `sudo -n` as `bs3d-api`: only `--port N` passes, into an environment of its own (`env -i`), from `/`, with stdin from `/dev/null`. `deploy/install-admin.sh`, which the owner runs as root, installs both and the sudoers rule for the account that ran it, checked with `visudo` and renamed into place; `update.sh` only says when a release carries a different launcher, so what may run as `bs3d-api` stays the owner's call. Both processes run as `bs3d-api` on a kernel without Yama: the page makes itself undumpable, and `bs3d-api.service` has `/dev/pts` out of reach (`InaccessiblePaths=`), since sudo gives the page a pseudo-terminal that belongs to `bs3d-api`. `PrivatePIDs=yes` was dropped in v0.1.15: under it systemd 257 took the service for a process not its own and stopped it with SIGKILL at once in 3 of 6 stops. `update.sh` puts each release's units in place (since v0.1.9) and puts the ones they replaced back on a rollback.
- **Configuration** is the `Scores` section (`ScoresOptions`), overridden by environment variables (`Scores__AddressSalt`, …). Outside Development the service **refuses to start without `Scores:AddressSalt`** — an unsalted hash of an address is a register of addresses. The content root is the binary's own folder, not the working directory (`Program.cs`): the Pi starts the service in `/var/lib/bs3d-api`, and without its `appsettings.json` the defaults log every request, player ids in the paths included.

## Conventions

The same as BS3D's, deliberately, since one owner and the same agents work on both:

- **Branches are the unit of work, and there are no pull requests.** A branch off `origin/main` named `<issue-number>-<slug>`, merged into `main` with `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`, pushed, and deleted locally and on the remote in the same breath.
- **Line endings are LF**, and `.gitattributes` says so.
- **Nothing secret is ever committed**: the tunnel's token, the salt for hashed addresses and the database live on the Pi only. The code is public on purpose — the security model (#2) assumes an attacker has read it.
- **Tests come with the behaviour**, unlike the game, which has none: a ranking can be wrong on every level while every number in it looks right (BS3D#173 is that failure in the game's own scoring), and the cases that catch it are cheap to write here.
- Comments and documents are load-bearing: change them in the same commit as the behaviour, and state a number only when it was measured.
- The owner communicates in Czech; code, comments and documents are in English.
